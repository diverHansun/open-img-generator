## 1. 背景与动机

用户原话（OpenCode，2026-09-07）：

> 目前图片文件生成后容易消失，甚至收藏的图片也容易无法加载。我建议保留之前：收藏的图片永远可见的方案，建议来把收藏过的图片存储到本地，然后在设置中可以管理/打开收藏图片放置的文件夹，你认为这个方案怎么样？查看现有代码实现，然后来和我通俗易懂讨论，提出你的建议！

根因在上一轮讨论中已对齐，本轮复验仍成立：fal / qwen / zhipu / siliconflow 等 URL 图只存远程引用；收藏只写 `favorites` 行并顺带触发浏览器下载；CDN 过期后应用内打不开。

## 2. 已确认：目标与范围

| 决策项 | 结论 |
|--------|------|
| 成功标准 | 新收藏只有字节落地才算成功；下载/转存失败必须明确失败，**不给假红心**。历史收藏若已失去唯一远程链接，保留红心与回溯信息并标示「原图已删除或丢失」，不承诺可恢复原图。 |
| 收藏成功定义 | **字节落地才算收藏成功**。失败回滚红心，并说明类似「这张已经存不了了」。 |
| 存储错误 | 把存储错误字段做正确、可映射到 UI；**KISS，不过度设计**（复用现有 `StorageError` / diagnostic，不新开错误体系）。 |
| 存储权威 | 复用现有应用受管目录（`getStorageRoot()`）。不另建用户可编辑的「收藏文件夹」当真相来源。 |
| 设置 | 只加「打开应用存储目录」。Web 显示以应用数据目录为基准的逻辑相对路径 `images/`，不返回主机绝对路径；桌面版提供打开实际目录的按钮。 |
| 使用场景 | 用户主要用 **Web 端**。因此钉盘以服务端下载为主；服务端因代理/Fake-IP 失败时，允许浏览器回传已取到的字节（同一套校验）。CORS 取不到字节则诚实失败，不建设代理系统。 |
| 旧收藏补救 | 不在 cleanup 或打开 Gallery 时自动下载。仍有 remote URL 的旧收藏在用户主动点「保存到本地」时走同一钉盘流程；已成为 `remote_expired` 墓碑的记录没有可下载来源，只显示「原图已删除或丢失」。 |
| 交互反馈 | 收藏或补存的一次点击依序尝试服务端下载、浏览器回传；两条路径都失败才回滚新收藏的红心。生成、详情、Gallery 复用工作区顶部提示卡片，按队列向下堆叠，统一 3 秒后收起；本地写入失败提示检查存储空间或目录权限，并保留重试入口。 |
| 文档落点 | `docs/mvp/probelm-list/2026-09-07-favorite-local-persistence/improve-1/`（沿用仓库既有 `probelm-list` 拼写）。仅一轮。 |
| 关键改动清单 | 不写。 |
| 外部参考项目 | 无，03 跳过。 |

## 6. 用户确认记录

规划会话中用户确认：

1. 本轮做完：新收藏在应用内可持续打开；失败不给假红心。已无法找回的历史收藏保留并标示「原图已删除或丢失」。设置做收藏图所在文件夹的打开按钮。
2. 字节落地才算收藏成功。失败回滚红心，并说明「这张已经存不了了」类似信息；存储错误字段要做好，但保证 KISS。
3. 只加「打开应用存储目录」，不做导出副本。
4. 主要用 Web；Web 无法打开目录则显示相对路径 `images/`，不泄露绝对路径。
5. 旧收藏只在用户主动点「保存到本地」时补钉；服务端失败后同次点击自动尝试浏览器回传。
6. 顶部提示卡片全局复用、向下堆叠、统一显示 3 秒；本地写入失败提示检查空间或目录权限。
